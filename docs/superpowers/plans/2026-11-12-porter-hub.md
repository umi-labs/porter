# Porter hub: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax.

**Goal:** A self-hosted hub (Docker on Dokploy, Better Auth) where:
- local porter projects push and pull versions
- staff and clients view results in a browser
- clients upload dumps
- stages run remotely by driving the porter binary

**Architecture:**
- `hub/` is a pnpm workspace with these packages:
  - `apps/web`: Next.js 15 App Router, Better Auth, API, SSE
  - `apps/worker`: Node, runs porter
  - `packages/db`: Drizzle schema and migrations, Postgres
  - `packages/porter`: spawns porter and parses NDJSON with zod
- Object storage is S3-compatible (MinIO in compose).
- New porter CLI `hub` commands live in `crates/porter-cli/src/commands/hub/`.

**Tech stack:** Next.js 15, React 19, Better Auth (organization, magic-link, device-authorization plugins; Google social provider), Drizzle ORM, Postgres 17, `@aws-sdk/client-s3` and the presigner, zod, Vitest, Playwright. The Rust CLI uses reqwest and keyring.

**Spec:** `docs/superpowers/specs/2026-11-12-porter-hub-design.md`

## Global Constraints

- The hub never deploys itself. Claude writes the Dockerfile, compose file and DEPLOY.md only.
- No secrets in the repo. All configuration comes from env, and `.env.example` lists every var.
- No client data in fixtures; use the engine's synthetic fixtures.
- Share links are read-only, expiring and revocable, stored as a token hash, and never expose raw data or submissions.
- Run secrets are encrypted at rest with `HUB_SECRET_KEY` (AES-256-GCM), never returned by the API after save, and passed to porter only as env.
- Remote runs never execute the `wp-db` connector. The worker removes it from the run's config and records an access-gap note in the run.
- Every API route checks the caller's project role, and the role checks have tests.
- The porter CLI hub commands follow the CLI contract: `--json`, exit codes, no prompts without `--interactive`, and the token kept in the keychain or `PORTER_HUB_TOKEN`.

## Review Focus

1. **Authorization leaks:** a client role reading another project, or raw data through a share link. Pinned in Task 3 (`permissions.test.ts` matrix).
2. **Interrupted multi-GB uploads** resume, and a completed upload's hash is verified. Pinned in Task 6.
3. **Push race:** two developers push from the same base; the second push is refused unless `--force`. Pinned in Task 8.
4. **Worker crash mid-run:** the run is marked failed after a lease timeout and the base version is untouched. Pinned in Task 7.
5. **Malformed NDJSON or porter crashing:** the run ends in `failed` with stderr captured, never "running" forever. Pinned in Task 7.

### Task 4: Storage, versions, media, push and pull API

**Files:** `hub/apps/web/lib/storage.ts`, `app/api/projects/[id]/versions/**`, `app/api/projects/[id]/media/**`

**API:**
- `POST /versions/init { base_version, media_hashes[] }` → the missing hashes plus presigned PUT URLs for the snapshot and the missing media.

### Task 6: Client uploads

**Files:** `hub/apps/web/app/(app)/p/[slug]/uploads/**`, `app/api/projects/[id]/uploads/**`, `components/uploader.tsx`

**Behaviour:**
- **Uploads:** S3 multipart with presigned part URLs, 16 MB parts, client-side retry per part, and resume by listing the uploaded parts.
- **Verification:** SHA-256 is computed client-side in a streaming worker and verified server-side after completion (the worker streams the object and hashes it).

### Task 7: Worker and remote runs

**Files:** `hub/apps/worker/src/{index.ts,claim.ts,execute.ts}`, `hub/packages/porter/{spawn.ts,events.ts}`, `app/api/projects/[id]/runs/**`, `app/(app)/p/[slug]/runs/[id]/page.tsx` (SSE)

**Behaviour:**
- **Claiming:** `SELECT … FOR UPDATE SKIP LOCKED` with a lease (heartbeat every 15 s; a lease older than 60 s is reclaimed and the run marked failed "worker lost").
- **Setup:** download the base version and media into a scratch dir; strip `wp-db` connectors (record an access-gap note); decrypt run secrets into env.
- **Execution:** spawn `porter --json --project <dir> …`; parse stdout as NDJSON with the zod v1 schemas into `run_event` rows plus `NOTIFY`, and capture stderr.
- **Completion:** on exit, upload the result as a new version, then set state and exit code.
- **Cancel:** sends SIGINT.
- **Concurrency:** one run per project.

**Steps:**
- [ ] **Step 1:** Failing tests:
  - `events parsed and stored in order`
  - `malformed line recorded and run continues`
  - `porter crash → failed with stderr`
  - `lease expiry reclaims`
  - `wp-db stripped with note`
  - `secrets only in env`: the spawned env contains them and the config files don't.
- [ ] **Step 2:** Run the tests. Expected: FAIL.
- [ ] **Step 3:** Implement. Tests use the real porter binary (built from the workspace) on the WXR fixture.
- [ ] **Step 4:** Run the tests. Expected: PASS.
- [ ] **Step 5:** Commit: `feat(hub): worker and live remote runs`.

### Task 8: porter CLI hub commands

**Files:** `crates/porter-cli/src/commands/hub/{mod.rs,login.rs,link.rs,push.rs,pull.rs,run.rs,uploads.rs}`, `crates/porter-engine/src/config.rs` (`[hub] url, project` with no secrets)

**Behaviour:**
- **Login:** device flow; the token goes in the keychain (service `porter-hub`); `PORTER_HUB_TOKEN` overrides.
- **Push:**
  - snapshot (excluding `media/`)
  - init with media hashes
  - upload the missing pieces
  - commit
  - a 409 → exit 1 "hub has version N; pull first or --force"
- **Pull:** refuses if the local project changed since the last sync (`.porter-hub.json` records the synced version and the project.db hash) unless `--force`.
- **Run:** streams SSE events to stdout exactly like a local run, then pulls.
